# Этап 1. Требования и минимальная воронка

Статус: реализовано в коде, готово к внутренней приёмке владельцами продукта,
медицинской безопасности и персональных данных.

## Цель и измеряемый результат

ИИ-чат помогает посетителю vodc.ru определить потребность, выбрать услугу,
врача и свободный слот из МИС, после чего открывает штатную точку записи.
Персональные данные пользователь вводит только в штатной форме.

Основной KPI MVP — доля начатых диалогов, дошедших до подтверждённого перехода
на точку записи. Факт создания записи с диалогом не связывается.

## Границы MVP

Разрешено:

- организационная информация из утверждённого реестра источников;
- подготовка к исследованию только по утверждённому источнику;
- поиск ограниченного каталога услуг и актуальной цены через МИС;
- выбор врача, филиала и слота только по идентификаторам МИС;
- параметризованный переход в штатную запись;
- одно проактивное приглашение без профилирования пользователя.

Запрещено:

- диагноз, оценка симптомов, назначение или изменение лечения;
- интерпретация анализов и исследований;
- создание, изменение или отмена записи;
- сбор ФИО, телефона, email, документов и медицинских идентификаторов;
- передача текста диалога в Метрику или технические логи;
- выдумывание цены, врача, филиала или слота при недоступности МИС;
- свободный вызов инструментов по решению LLM.

## Каталог намерений

| Intent | Пример | RAG | МИС | Поведение |
|---|---|---:|---:|---|
| `service_search` | «Нужно МРТ» | да | да | показать ограниченный список услуг |
| `doctor_search` | «Нужен кардиолог» | да | да | сначала определить услугу, затем врача |
| `preparation` | «Как подготовиться к УЗИ?» | да | нет | ответить по утверждённому источнику |
| `price` | «Сколько стоит КТ?» | да | да | цена только из МИС |
| `availability` | «Есть время завтра?» | да | да | слоты после выбора услуги |
| `booking` | «Как записаться?» | да | да | провести по воронке до redirect |
| `organizational_info` | «Где находится центр?» | да | нет | ответить без изменения воронки |
| `unknown` | «Расскажите подробнее» | да | нет | ответить по источникам или уточнить |

До intent-классификации всегда выполняется safety gateway. Emergency,
medical-refusal, prompt-injection и PII являются решениями безопасности, а
не бизнес-намерениями. Заблокированный input не сохраняется в raw-сессии.

Для намерений, требующих МИС, итоговый текст формируется детерминированно,
а актуальные значения выводятся в карточках. RAG-контекст не передаётся LLM
для ответа о цене, враче, расписании или слоте.

## Состояния воронки

| Состояние | Вход | Результат |
|---|---|---|
| `discovery` | новый диалог | определение потребности |
| `need_clarification` | неясный запрос | один уточняющий вопрос |
| `service_shortlist` | МИС вернула услуги | карточки релевантных услуг |
| `service_selected` | подписанный выбор услуги | врачи или доступное время |
| `doctor_selected` | подписанный выбор врача | актуальные слоты |
| `slot_selected` | подписанный выбор слота | предложение перейти к записи |
| `booking_redirect` | повторная проверка слота | URL штатной формы |
| `safe_stop` | экстренный сценарий | прекращение коммерческой воронки |

Информационные запросы не продвигают пользователя по коммерческой воронке.
Выбор карточек, переходы состояний и права инструментов детерминированы.

## События и KPI

События не содержат пользовательского текста.

| Показатель | Формула | Источник |
|---|---|---|
| Начатые диалоги | `count(chat_started)` | `funnel_events` |
| Выбор услуги | `count(select_service)` | `funnel_events` |
| Переходы к записи | `count(booking_redirect)` | `funnel_events` |
| Конверсия в услугу | уникальные сессии `select_service` / `chat_started` | выгрузка |
| Главный KPI | уникальные сессии `booking_redirect` / `chat_started` | выгрузка |
| Отказы МИС | `mis_available=false` в `message_completed` | выгрузка |
| Распределение потребностей | `intent` в `message_completed` | выгрузка |
| Время ответа | p50/p95 `vodc_chat_stream_duration_seconds` | Prometheus |
| Технические ошибки | `vodc_chat_errors_total` | Prometheus |

До пилота измеряется техническая корректность событий. Бизнес-baseline
собирается в первую неделю opt-in пилота; улучшение оценивается относительно
этого baseline, поскольку исторической атрибуции диалог → запись нет.

## Критерии готовности этапа

- каталог намерений реализован единым детерминированным модулем;
- все состояния и переходы покрыты unit/API-тестами;
- запрещённые медицинские запросы не достигают LLM и МИС;
- организационный запрос не вызывает МИС и не изменяет воронку;
- динамические сущности приходят только из МИС;
- `chat_started`, `select_service`, `booking_redirect`, intent и latency
  доступны для расчёта KPI;
- тексты emergency/refusal утверждаются медицинским владельцем до пилота;
- ограниченный production-каталог услуг утверждается бизнес-владельцем.

Последние два пункта требуют решения Заказчика и отражены как внешние входы,
а не заменяются тестовыми утверждениями. До заполнения
`config/service_priorities.json:allowed_service_ids` каталог работает
fail-closed и не показывает ни одной услуги.
